# B10 · Refugios y Almas Afines

## Objetivo

Un refugio es la conversación privada donde alguien cuenta lo que no ha contado
nunca: 1:1 o círculo de hasta 8 personas, **cifrado de extremo a extremo en el
navegador**, con el servidor guardando solo `ciphertext` y `nonce` y sin poseer
jamás la clave. Alrededor van las Almas Afines —libreta de contactos con estado
de disponibilidad—, el bloqueo y el silencio aplicados en RLS, el botón de crisis
siempre visible y el aviso cuando alguien de tu lista pide hablar. Es el bloque
con más superficie de riesgo de Darma: aquí un fallo no degrada la experiencia,
expone a una persona.

## Qué construir

1. **Migración `0010_b10_claves.sql`** — el directorio de claves públicas y los
   sobres. El servidor guarda material **público** y material **ya cifrado**;
   nada más:

   ```sql
   -- Clave pública de identidad de cada persona. PÚBLICA por definición: sirve
   -- para que otros deriven un secreto compartido con ella.
   create table public.user_keys (
     user_id      uuid primary key references public.profiles(id) on delete cascade,
     -- JWK pública de ECDH P-256 (crv P-256, x, y). Sin la parte privada.
     public_jwk   jsonb not null,
     -- Huella SHA-256 de la JWK canonicalizada. Es el "número de seguridad" que
     -- dos personas comparan para detectar una suplantación del servidor.
     fingerprint  text not null,
     -- Sube al rotar (dispositivo nuevo). Los sobres viejos quedan ilegibles.
     key_version  smallint not null default 1,
     created_at   timestamptz not null default now(),
     rotated_at   timestamptz
   );

   -- La clave simétrica del refugio, CIFRADA para cada miembro con el secreto
   -- ECDH entre quien invita y quien recibe. El servidor ve un blob y nada más.
   create table public.refuge_key_envelopes (
     refuge_id    uuid not null references public.refuges(id) on delete cascade,
     recipient_id uuid not null references public.profiles(id) on delete cascade,
     sender_id    uuid not null references public.profiles(id) on delete cascade,
     -- AES-KW / AES-GCM sobre la clave del refugio. Opaco.
     wrapped_key  bytea not null check (octet_length(wrapped_key) between 16 and 512),
     wrap_nonce   bytea not null check (octet_length(wrap_nonce) between 12 and 24),
     -- Huella de la clave pública del emisor EN EL MOMENTO de envolver: permite
     -- detectar que alguien rotó y el sobre ya no corresponde.
     sender_fingerprint text not null,
     key_version  smallint not null default 1,
     created_at   timestamptz not null default now(),
     primary key (refuge_id, recipient_id)
   );

   -- Copia de seguridad OPCIONAL de la clave de identidad, envuelta con una
   -- frase de recuperación que el servidor NUNCA ve. Sin frase, no hay backup.
   create table public.identity_backups (
     user_id     uuid primary key references public.profiles(id) on delete cascade,
     wrapped_identity bytea not null,
     kdf_salt    bytea not null,
     kdf_iterations integer not null check (kdf_iterations >= 600000),
     created_at  timestamptz not null default now()
   );
   ```

   RLS y privilegios:
   - `user_keys`: `select` para `authenticated` con `using (true)` — una clave
     pública es pública; ocultarla no aporta seguridad y rompe el intercambio.
     `insert`/`update` solo sobre la propia fila (`user_id = (select auth.uid())`).
   - `refuge_key_envelopes`: `select` **solo** `recipient_id = auth.uid()`;
     `insert` solo si `sender_id = auth.uid()` **y**
     `public.is_refuge_member(refuge_id, (select auth.uid()))` **y**
     `not public.refuge_has_block(refuge_id, recipient_id)`.
     `revoke update, delete`: un sobre no se edita, se sustituye borrando la
     pertenencia.
   - `identity_backups`: `select`/`insert`/`delete` solo sobre la propia fila.
   - Índice: `create index idx_envelopes_recipient on public.refuge_key_envelopes
     (recipient_id, refuge_id);` — el acceso real es «dame mis sobres».

2. **`lib/crypto/` — el esquema, decidido.** No investigues alternativas; esto ya
   está elegido y el porqué está aquí:

   - **Algoritmo de mensaje: AES-256-GCM con nonce de 12 bytes** (`enc_version = 1`).
     `0002` menciona XChaCha20-Poly1305 en un comentario, pero **WebCrypto no lo
     implementa** y meter una librería de cifrado en el bundle añade ~40 KB y una
     dependencia de terceros en el camino más sensible de la app. AES-GCM es
     nativo, auditado por el navegador y cabe en el `check (octet_length(nonce)
     between 12 and 24)` del esquema. El `ciphertext` incluye el tag de 16 bytes.
   - **Nonce: 12 bytes de `crypto.getRandomValues` por mensaje.** Nunca un
     contador, nunca derivado del `id`: reutilizar un nonce con la misma clave en
     GCM **revela el XOR de los dos textos y permite falsificar mensajes**. Es el
     único fallo de este bloque que rompe el cifrado por completo.
   - **Intercambio de claves: ECDH P-256 + HKDF-SHA256.** Cada persona genera un
     par ECDH P-256 (`extractable: false` salvo para el backup, §4) y publica la
     JWK pública en `user_keys`. Quien crea el refugio genera una clave AES-256
     aleatoria (la clave del refugio), deriva con ECDH un KEK con cada miembro y
     sube un `refuge_key_envelopes` por persona. Se eligió P-256 y no X25519
     porque X25519 aún no está en todos los navegadores que Darma debe soportar;
     P-256 lleva años en WebCrypto en todos.
   - **Almacenamiento local: IndexedDB con `CryptoKey` no extraíble.** No
     `localStorage` (es texto plano y accesible desde cualquier XSS): un
     `CryptoKey` no extraíble no se puede exfiltrar ni con ejecución de JS en la
     página, solo *usar* mientras la pestaña esté abierta.

3. **Suplantación por parte del servidor (lo que hay que asumir y mitigar).** Si
   Darma sirviera una `public_jwk` falsa, podría interponerse. No se puede evitar
   por completo en una web app —el servidor sirve el propio JS—, así que se hace
   lo que sí se puede: mostrar el **número de seguridad** (los primeros 60 bits del
   `fingerprint`, en grupos de 5 dígitos) en la pantalla del refugio, y **avisar en
   la conversación** cuando la huella de la otra persona cambie
   («El dispositivo de esta persona ha cambiado; los mensajes anteriores no se
   pueden leer con la clave nueva»). Ese aviso es un mensaje de sistema
   (`refuge_messages.kind = 'system'`), no un toast que se pierde.

4. **Pérdida del dispositivo — la decisión difícil, escrita para el usuario.**
   Por defecto **la clave vive solo en el dispositivo y perderlo significa perder
   el historial**. No hay recuperación por email, ni por soporte, ni por
   verificación de identidad: cualquiera de esas cosas obligaría a que Darma
   tuviera la clave, y entonces el cifrado extremo a extremo sería teatro.
   Lo que sí se ofrece, **desactivado por defecto y con opt-in explícito**:
   - Una **frase de recuperación de 12 palabras** generada en el cliente.
   - `PBKDF2-SHA256`, ≥ 600 000 iteraciones, sal de 16 bytes aleatoria → KEK.
   - La clave de identidad se exporta **una sola vez** en el momento de crear el
     backup, se envuelve con ese KEK y se sube a `identity_backups`. A partir de
     ahí la copia local vuelve a ser no extraíble.
   - La pantalla de activación dice literalmente las tres cosas: *quien tenga la
     frase puede leer todo tu historial*, *Darma no puede recuperarla si la
     pierdes* y *sin backup, cambiar de móvil borra tus conversaciones*.
   Al entrar en un dispositivo nuevo sin backup: se genera un par nuevo, se sube
   con `key_version + 1`, y la app muestra los refugios **con el historial
   ilegible y un aviso claro**, no una pantalla vacía que parezca un bug. Los
   miembros pueden reenviar el sobre con la clave del refugio, y a partir de ese
   punto los mensajes **nuevos** se leen. Los antiguos, no: ese es el precio.

5. **`GET /api/refuges`** — bandeja. Keyset sobre `idx_refuges_activity`:
   `where archived_at is null and (last_message_at, id) < (:ts, :id) order by
   last_message_at desc, id desc limit 20`. Los no leídos salen de comparar
   `refuge_members.last_read_message_id` con el último id, **no** de contar.

6. **`GET /api/refuges/[id]/mensajes?cursor=&limite=`** — historial por keyset
   sobre `idx_refuge_messages_keyset`: `where refuge_id = :r and state = 'active'
   and id < :cursor order by id desc limit 50`. Devuelve `ciphertext` y `nonce`
   en base64; el descifrado ocurre **solo** en el cliente.

7. **`POST /api/refuges/[id]/mensajes`** — body `{ ciphertextB64, nonceB64,
   encVersion, kind, byteSize }`. El servidor **no valida el contenido** porque no
   puede: valida tamaños, `kind`, y que el remitente sea miembro (aunque RLS ya lo
   hace, la ruta lo comprueba para devolver un error humano). El `sender_id` sale
   de la sesión. Rate limit `refuge_msg:${userId}` 30/min.

8. **Realtime.** `supabase.channel('refuge:'+id).on('postgres_changes', { event:
   'INSERT', schema: 'public', table: 'refuge_messages', filter: 'refuge_id=eq.'+id })`.
   Realtime **respeta RLS**, así que un no miembro no recibe nada; aun así, filtra
   por `refuge_id` en el cliente y **descarta** cualquier payload cuyo `refuge_id`
   no coincida. Reconexión: al recuperar el canal, pide el keyset desde el último
   `id` conocido — un `INSERT` perdido durante la desconexión no vuelve solo.

9. **Almas Afines.** `GET /api/refuges/kindred` lee `kindred` con join por PK a
   `profiles` (`alias`, `avatar_seed`, `level`, `availability`). `POST` y `DELETE`
   sobre la lista; `PATCH` solo de `note` (es la única columna con `grant update`).
   Estado de disponibilidad: `disponible` / `necesito_hablar` / `ausente`, tomado
   de `profiles.availability`.

10. **Aviso de crisis de un contacto — con el límite bien puesto.** La señal que
    ven tus almas afines es **exclusivamente** `availability = 'necesito_hablar'`,
    que la persona pone ella misma. `crisis_events` **no tiene ninguna política
    RLS** y no debe filtrarse por ningún camino: avisar automáticamente a tus
    contactos de que el clasificador te marcó en riesgo sería revelar tu estado de
    salud mental a terceros sin tu consentimiento, y convertiría la app en algo que
    la gente dejaría de usar para hablar en serio. Lo que sí hace B10: cuando el
    flujo de crisis de B11 termina, **ofrece** a la persona poner
    `necesito_hablar`; si acepta, sus almas afines lo ven. Es opt-in, siempre.

11. **Crisis dentro de un refugio.** El servidor no puede leer el mensaje, así que
    `evaluarRiesgo()` (`lib/crisis.ts`) se ejecuta **en el cliente, sobre el texto
    en claro, antes de cifrar**. Si el nivel es `high`/`critical`: se muestra la
    tarjeta de recursos **en la misma interacción**, y se envía a
    `POST /api/refuges/crisis` **solo el nivel de riesgo y el `refuge_id`** para
    escribir `crisis_events`. **Nunca el texto.** El mensaje se envía igualmente:
    se prioriza, no se censura (`CONTRATOS.md` §9).

12. **Pantallas.** `app/(app)/refugios/page.tsx` (bandeja, Server Component),
    `app/(app)/refugios/[id]/page.tsx` (hilo; el shell es server, el hilo es
    `'use client'` porque necesita WebCrypto e IndexedDB).
    `components/refuge/`: `ListaRefugios`, `Hilo`, `Burbuja`, `Redactor`,
    `NumeroSeguridad`, `AvisoClaveCambiada`, `ListaAlmasAfines`, `MenuBloquear`,
    `DialogoFraseRecuperacion`. `BotonCrisis` **siempre visible**, fijo, también
    cuando el teclado está abierto en móvil.

## Consultas y rendimiento

```sql
-- Bandeja (keyset, sin contar mensajes)
select r.id, r.kind, r.title, r.member_count, r.last_message_at, r.message_count,
       m.last_read_message_id, m.muted
  from public.refuges r
  join public.refuge_members m on m.refuge_id = r.id and m.user_id = :yo and m.left_at is null
 where r.archived_at is null
   and (r.last_message_at, r.id) < (:cursor_ts, :cursor_id)
 order by r.last_message_at desc, r.id desc
 limit 20;

-- Hilo (el índice más caliente de la app)
select id, sender_id, ciphertext, nonce, enc_version, kind, created_at
  from public.refuge_messages
 where refuge_id = :r and state = 'active' and id < :cursor
 order by id desc
 limit 50;
```

`idx_refuges_activity` e `idx_refuge_messages_keyset` cubren los dos `where` +
`order by` enteros. El `id` es `bigint identity`, así que **es** el orden
cronológico y el cursor a la vez: no hace falta ordenar por `created_at` (que no
es único y produciría un cursor ambiguo con dos mensajes en el mismo milisegundo).

Coste de las políticas: `is_refuge_member` y `refuge_has_block` son `stable` +
`security definer`, así que el planificador las evalúa como InitPlan **una vez por
consulta**, no por fila. No las conviertas en subconsultas inline «para ahorrar
una función»: además de perder eso, `refuge_members` consultándose a sí misma
dispara `infinite recursion detected in policy`.

Realtime: un canal por refugio abierto, **uno solo**. Cerrarlo al desmontar. Con
cientos de miles de usuarios, un canal por refugio de la bandeja son miles de
suscripciones por cliente y tumba el servicio de Realtime.

Presupuesto: `/refugios` ≤ 3 consultas, `/refugios/[id]` ≤ 2 + el canal.
Descifrado en lote de la página de 50 mensajes con `Promise.all`, no en serie
dentro del render.

## Seguridad

**Lo que no debe pasar nunca** (léelo como una lista de fallos, no de deseos):

- **Que un texto en claro llegue al servidor.** Ni en el body, ni en un campo
  «preview», ni en el `title` del refugio, ni en un log, ni en el payload de una
  push. La notificación de B13 dice «tienes un mensaje nuevo en un refugio» y
  nada más: anótalo en `PEDIDOS.md` para B13 de forma explícita.
- **Que se reutilice un nonce.** 12 bytes aleatorios por mensaje, siempre.
- **Que la clave de identidad se guarde extraíble.** `extractable: false` salvo el
  instante único del backup opt-in.
- **Que un bloqueo se aplique solo en la UI.** Ya está en el `using` de las
  políticas de `0002`; tu trabajo es **no rodearlo**: prohibido el cliente admin en
  cualquier lectura de refugios, mensajes, `kindred` o perfiles. Si te descubres
  usando `createAdminClient()` en este bloque fuera del cron, es un bug de diseño.
- **Que se filtre `crisis_events` a las almas afines.** Ver §10.
- **Que un no miembro pueda distinguir «no tengo acceso» de «no existe».** `0002`
  lo garantiza devolviendo cero filas; tu API debe devolver `no_encontrado`
  (404) en ambos casos, **nunca** `sin_permiso` (403), que confirmaría que la sala
  existe. Para un acosador, esa confirmación es la información que busca.
- **Que se pueda editar un mensaje ya leído.** `0002` revoca todo `update` salvo
  `state`. No intentes «editar» borrando y reinsertando.
- **Que el `id` del refugio venga del body en una acción destructiva.** Va en la
  ruta y se valida como uuid; el `userId`, siempre de la sesión.
- **Que se active micrófono o cámara.** `Permissions-Policy` los deniega a nivel
  de navegador y `refuge_messages.kind` admite `'audio'` **solo** como formato de
  archivo cifrado subido, no como grabación en la app. En este bloque, `'audio'`
  no se implementa.

Rate limits: mensajes 30/min por usuario, creación de refugio 5/hora,
`kindred` 20/min, `bloquear` 20/min, `keys` (POST) 3/día — rotar la clave de
identidad tres veces al día no es un uso legítimo, es una sonda.

## Pruebas exigidas

1. Ida y vuelta: `cifrar` → `descifrar` con la misma clave devuelve el texto; con
   una clave distinta **lanza** (GCM falla la autenticación) y la UI marca
   `ilegiblePorClave: true` en vez de romperse. **Camino de fallo.**
2. Un `ciphertext` manipulado en un solo bit **no** descifra (el tag GCM lo
   detecta). **Fallo.**
3. Dos llamadas a `cifrar` con el mismo texto y la misma clave producen **nonces
   distintos**; 1 000 llamadas no repiten ninguno.
4. `envolverParaMiembro` + `abrirSobre` entre dos pares ECDH distintos recupera la
   misma clave de refugio; con la clave pública de un tercero, falla. **Fallo.**
5. `huella` es estable ante reordenación de las propiedades de la JWK (se
   canonicaliza antes de hashear) y cambia si cambia `x` o `y`.
6. Frase de recuperación: 12 palabras → PBKDF2 (≥ 600 000) → envolver →
   desenvolver recupera la identidad; con **una palabra cambiada**, falla y el
   mensaje de error no dice cuál. **Fallo.**
7. **Camino de fallo:** `GET /api/refuges/[id]/mensajes` sobre un refugio del que
   no eres miembro → **404 `no_encontrado`**, nunca 403, y el cuerpo no distingue
   ese caso de un uuid inexistente.
8. **Camino de fallo:** con un `blocks` vivo entre dos miembros, el refugio
   desaparece para ambos (`refuge_has_block`), `POST .../mensajes` devuelve error
   y `POST /api/refuges/kindred` con la persona bloqueada falla por la política.
9. Keyset del hilo: con 500 mensajes sembrados, tres páginas de 50 no repiten ni
   se saltan ninguno; cursor corrupto → 422 `entrada_invalida`.
10. Realtime: un payload con `refuge_id` distinto al del canal se descarta en el
    cliente; tras una reconexión se piden por keyset los mensajes desde el último
    `id` conocido y no queda ningún hueco.
11. `POST /api/refuges/crisis` con un campo `texto` en el body → **422**: el
    esquema zod es `strict()` y rechaza campos no declarados. **Fallo. Este test
    es obligatorio**: es el que impide que alguien añada «solo un preview» dentro
    de seis meses.
12. Ninguna respuesta de `kindred` contiene `email`, `karma_spendable`,

## Trampas conocidas

1. **Guardar la clave en `localStorage` «mientras tanto».** Es texto plano y
   cualquier XSS la lleva. IndexedDB con `CryptoKey` no extraíble desde el primer
   commit; migrar después significa que las claves ya filtradas siguen filtradas.
2. **Derivar el nonce del `id` del mensaje «para ahorrar bytes».** Con AES-GCM,
   dos mensajes con el mismo nonce y la misma clave revelan el XOR de sus textos y
   permiten falsificar. Es el único fallo de este bloque que anula el cifrado
   entero, y parece una optimización inocente en un PR.
3. **Devolver 403 cuando no eres miembro.** `0002` está construido para que un
   refugio sea *indistinguible de inexistente*; un 403 en tu API deshace ese
   trabajo y le confirma a un acosador que su víctima sigue en la app.
4. **Un canal de Realtime por cada refugio de la bandeja.** Con 40 refugios son 40
   suscripciones WebSocket por usuario. La bandeja se refresca al volver a ella o
   con un único canal a `refuge_members` filtrado por `user_id`; el canal de
   mensajes solo se abre en el hilo abierto.
5. **Avisar automáticamente a las almas afines de una crisis detectada.** Suena
   humano y es exactamente lo que no se puede hacer: revela un dato de salud
   mental a terceros sin consentimiento y hace que la gente deje de escribir con
   sinceridad. La señal es `availability`, puesta por la propia persona, siempre
   opt-in.
