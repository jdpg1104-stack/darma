# B13 · Notificaciones push y PWA

## Objetivo

Darma tiene que poder avisar a alguien de que **le escucharon**, o de que un Alma
Afín acaba de marcar «necesito hablar», sin convertirse en otra app que vibra
para reclamar atención. Este bloque construye Web Push con VAPID, la instalación
como PWA con offline básico, preferencias granulares por tipo de aviso y una
política antiadicción explícita y aplicada en código. El anonimato manda también
aquí: una notificación en la pantalla de bloqueo la lee cualquiera que pase por
delante del móvil.

## Qué construir

1. **Migración `0013_b13_push.sql`.** No modifiques `0001` ni `0002`. Crea:

```sql
create table public.push_subscriptions (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references public.profiles(id) on delete cascade,
  endpoint    text not null,
  p256dh      text not null,
  auth        text not null,
  user_agent_hash text,        -- HASH, jamás el user-agent en claro (§2 CONTRATOS)
  created_at  timestamptz not null default now(),
  last_ok_at  timestamptz
);
-- Un endpoint es único globalmente: reinstalar la PWA genera uno nuevo, y el
-- viejo hay que poder retirarlo aunque el usuario ya no lo recuerde.
create unique index uq_push_subscriptions_endpoint on public.push_subscriptions (endpoint);
create index idx_push_subscriptions_user on public.push_subscriptions (user_id);

create table public.notification_prefs (
  user_id     uuid primary key references public.profiles(id) on delete cascade,
  prefs       jsonb not null default '{}'::jsonb,
  -- Horas de silencio en la zona del usuario. Sin zona horaria identificable a
  -- nivel de ciudad: se guarda solo el offset en minutos.
  quiet_from  smallint check (quiet_from between 0 and 1439),
  quiet_to    smallint check (quiet_to between 0 and 1439),
  tz_offset   smallint not null default 0,
  updated_at  timestamptz not null default now()
);

alter table public.push_subscriptions enable row level security;
alter table public.notification_prefs enable row level security;

-- Cada quien ve y borra SOLO sus suscripciones. El insert va por el servidor.
create policy push_read_own on public.push_subscriptions
  for select to authenticated using (user_id = (select auth.uid()));
create policy push_delete_own on public.push_subscriptions
  for delete to authenticated using (user_id = (select auth.uid()));

create policy prefs_read_own on public.notification_prefs
  for select to authenticated using (user_id = (select auth.uid()));
create policy prefs_upsert_own on public.notification_prefs
  for insert to authenticated with check (user_id = (select auth.uid()));
create policy prefs_update_own on public.notification_prefs
  for update to authenticated
  using (user_id = (select auth.uid())) with check (user_id = (select auth.uid()));

revoke insert, update on public.push_subscriptions from anon, authenticated;
revoke update on public.notification_prefs from anon, authenticated;
grant  update (prefs, quiet_from, quiet_to, tz_offset) on public.notification_prefs to authenticated;
```

2. **VAPID gateado** (`lib/push/vapid.ts`). Depende de `web-push`; añádelo a
   `package.json` (es tu única modificación fuera de tu lista — anótala en
   `PEDIDOS.md`) o, si prefieres cero dependencias nuevas, implementa el JWT
   ES256 con `crypto.subtle`. Patrón obligatorio: `pushConfigurado(): boolean`.
   Sin `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` en el entorno, **el botón de opt-in
   no se pinta y el envío es un no-op silencioso**. Producción segura hasta que
   se provisionen las llaves; nunca un 500.

3. **Envío que no lanza** (`lib/push/enviar.ts`). `enviarA(sub, payload):
   Promise<'ok'|'gone'|'error'>`. Un 410 o 404 significa que el navegador ya no
   acepta esa suscripción: devuélvelo como `'gone'` y **borra la fila**. Sin esa
   limpieza, `push_subscriptions` acumula endpoints muertos y cada envío masivo
   paga N peticiones HTTP a un servicio que va a devolver 410. `enviarAVarias()`
   los agrupa con `Promise.allSettled` y borra los `gone` en un solo `delete ...
   in (...)`.

4. **Anonimato en el contenido del aviso.** Esta es la parte que distingue a
   Darma de cualquier otra app con push:
   - **El cuerpo de la notificación nunca contiene el texto del post ni del
     comentario.** «Alguien te escuchó» sí; las primeras 60 palabras del
     desahogo, no. Una notificación aparece en la pantalla de bloqueo y la lee
     quien pase por delante.
   - **El alias del emisor solo aparece si esa persona lo permite.** El campo
     `prefs.revelar_alias` es del **emisor**, no del receptor: si alguien
     desactiva revelar su alias, sus avisos llegan como «alguien», también a
     quien ya lo tenga como Alma Afín.
   - `lib/push/plantillas.ts` tiene, para cada tipo, **dos variantes**: con alias
     y sin alias. Elegir entre ellas es una decisión de servidor, hecha con los
     datos del emisor. Nunca del receptor y nunca del cliente.
   - El `payload` que sale por la red lleva solo `{tipo, titulo, cuerpo, url}`.
     Ni `postId` con el cuerpo, ni `authorId` en claro cuando el alias está
     oculto: el service worker no debe tener material para reconstruirlo.
   - Nada de `user_agent` ni `ip` almacenados (§2 de `CONTRATOS.md`); si necesitas
     distinguir dispositivos, guarda un hash con sal.

5. **Preferencias granulares** (`lib/push/preferencias.ts`). Tipos permitidos y
   sus defaults:

   | Tipo | Default | Qué avisa |
   |---|---|---|
   | `te_escucharon` | ON | Alguien comentó tu post y su comentario se validó |
   | `te_ayudo` | ON | El autor marcó tu comentario como «me ayudó» |
   | `alma_afin_en_crisis` | ON | Un Alma Afín puso `necesito_hablar` |
   | `mensaje_refugio` | ON | Mensaje nuevo en un refugio (respeta `muted`) |
   | `respuesta_hilo` | OFF | Alguien más comentó en un hilo donde participas |
   | `nivel_alcanzado` | OFF | Subiste de nivel |
   | `revelar_alias` | ON | (del emisor) permitir que tu alias salga en los avisos ajenos |

   `sanitizarPrefs(input: unknown): Preferencias` descarta claves desconocidas.
   El `jsonb` viene del cliente y **el cliente puede escribirlo directamente vía
   PostgREST** (tiene `grant update (prefs)`): trata su contenido como no
   confiable en cada lectura, no solo al guardarlo.

6. **Política antiadicción (requisito, no recomendación).** Escríbela como
   constantes y como tests, no como comentario:
   - **Prohibido**: rachas, «vuelve, te echamos de menos», «tienes 3 posts sin
     leer», recuentos de actividad ajena, cualquier aviso cuyo propósito sea
     reabrir la app sin que haya pasado nada dirigido a esta persona. Si un tipo
     de notificación no puede completar la frase «alguien hizo X **por ti**», no
     existe.
   - **Techo duro**: máximo 4 notificaciones por persona y día para todo lo que
     no sea `alma_afin_en_crisis`. Contador con
     `check_rate_limit('push:'||userId, 4, 86400)`.
   - **Agrupación**: si hay varios eventos del mismo tipo en 30 minutos, se manda
     uno solo, agregado («3 personas te escucharon»).
   - **Horas de silencio**: por defecto 23:00–08:00 en la zona del usuario. Lo
     acumulado se entrega al terminar el silencio, no se descarta.
   - **La única excepción a todo lo anterior es `alma_afin_en_crisis`**, que
     ignora techo, agrupación y horas de silencio. Alguien que puso «necesito
     hablar» a las 3 de la madrugada es exactamente el caso para el que existe
     este bloque. La crisis gana siempre, también aquí.

7. **Momento del opt-in** (`components/pwa/OptInPush.tsx`). **No pidas permiso al
   cargar la app.** Un `Notification.requestPermission()` en el primer render se
   deniega y el navegador **bloquea el origen permanentemente**: no hay segunda
   oportunidad. Pídelo justo después del primer momento en que la notificación
   tiene sentido para esa persona —cuando su primer comentario se valida, o
   cuando guarda su primera Alma Afín—, con una explicación previa en la UI y un
   «ahora no» que pospone 7 días en `localStorage`. Registra si se mostró, si se
   aceptó y si se descartó, sin ningún dato del usuario.

8. **`public/sw.js`.** JavaScript plano (no pasa por el bundler). Contenido:
   - `install`: precachear el shell (`/`, `/feed`, `/ayuda`, `/offline`, CSS
     crítico). **`/ayuda` va en el precache**: los recursos de crisis tienen que
     funcionar sin red.
   - `fetch`: network-first para navegación con caída a `/offline`;
     stale-while-revalidate para estáticos. **Nunca cachees `/api/**`**: cachear
     el feed sirve desahogos rancios y, peor, deja contenido de otra persona en
     el disco de esta.
   - `push`: parsea el JSON, muestra `showNotification` con `tag` por tipo para
     que la agrupación colapse en el sistema.
   - `notificationclick`: `clients.matchAll` → enfocar la pestaña existente si la
     hay, `openWindow` si no.
   - Versionado de caché (`const CACHE = 'darma-v1'`) y borrado de versiones
     viejas en `activate`. Sin esto, un usuario se queda con el shell de hace
     tres meses y no hay forma de sacarlo de ahí.

9. **`public/manifest.json`.** `name`, `short_name: "Darma"`, `start_url: "/feed"`,
   `scope: "/"`, `display: "standalone"`, `theme_color`/`background_color`
   tomados de los tokens de `app/globals.css` (no inventes hex), iconos 192/512
   maskable. `orientation: "portrait"`. Sin `share_target`: aceptar contenido
   compartido de otras apps es una vía de entrada sin moderar.

10. **Offline básico** (`components/pwa/AvisoSinConexion.tsx`). Escucha
    `online`/`offline`. Sin conexión: banner discreto, composer deshabilitado con
    explicación (nada de encolar posts para enviarlos luego — un desahogo escrito
    a las 3 AM y publicado a las 9 sin que su autor lo recuerde es un problema de
    consentimiento, no una función), y `/ayuda` accesible desde caché.

11. **Rutas.** Cinco, todas bajo `/api/push/`. `subscribe` valida la forma de la
    suscripción con zod (`endpoint` debe ser `https:` y de un host de servicio
    conocido) y hace upsert por `endpoint`.

## Consultas y rendimiento

- Suscripciones de una persona (usa `idx_push_subscriptions_user`):

```sql
select id, endpoint, p256dh, auth from public.push_subscriptions where user_id = :u;
```

- Destinatarios de un aviso de disponibilidad. El sentido inverso de `kindred`
  ya está indexado (`idx_kindred_reverse`) exactamente para esto:

```sql
select k.owner_id
  from public.kindred k
 where k.kindred_id = :quien_necesita_hablar
   and not public.is_blocked_between(k.owner_id, k.kindred_id);
```

  Sin `idx_kindred_reverse` esto es un seq scan de la tabla entera cada vez que
  alguien cambia su disponibilidad — y ese cambio es frecuente.
- **Nunca `count(*)` sobre `push_subscriptions`** para pintar «N dispositivos»:
  lee la lista, que está acotada por persona.
- El envío masivo se hace por lotes de 100 con `Promise.allSettled`; un
  destinatario que tarda no puede bloquear a los demás.
- Presupuesto: `components/pwa/**` ≤ 15 KB de JS comprimido. `sw.js` ≤ 8 KB.
  El opt-in es la hoja `'use client'` más pequeña posible; el resto, servidor.
- `EXPLAIN ANALYZE` de la consulta de destinatarios en el PR.

## Seguridad

- `VAPID_PRIVATE_KEY` es secreta. Solo `NEXT_PUBLIC_VAPID_PUBLIC_KEY` (o el
  endpoint `/api/push/key`) llega al navegador. Una clave privada VAPID filtrada
  permite a un tercero enviar notificaciones que el navegador acepta como
  nuestras.
- El `userId` de una suscripción sale de la sesión, nunca del body. Si aceptas
  `userId`, cualquiera suscribe su dispositivo a los avisos de otra persona — y
  en esta app eso es saber cuándo alguien está en crisis.
- Valida el `endpoint`: `https:` obligatorio y host en una allowlist de servicios
  de push conocidos. Un endpoint arbitrario convierte tu servidor en un
  proxy de peticiones salientes (SSRF).
- **El bloqueo se aplica antes de enviar**: llama a `is_blocked_between()` o
  filtra por `blocks` en la consulta. Que alguien bloqueado no pueda escribirte
  pero sí hacer vibrar tu teléfono sería un agujero grande.
- Un miembro con `refuge_members.muted = true` no recibe `mensaje_refugio`.
- `sanitizarPrefs` en cada lectura: el `jsonb` es escribible por el cliente vía
  PostgREST.
- Rate limit en `subscribe` y en `PATCH /prefs`.
- La CSP de `next.config.ts` no necesita cambios para push (el service worker es
  del mismo origen y `web-push` corre en el servidor). **Si te ves tocando la
  CSP, párate**: casi seguro estás cargando algo de un tercero, y en esta app
  eso está prohibido por diseño.

## Trampas conocidas

1. **`proxy.ts` no excluye `manifest.json`.** El `matcher` excluye
   `manifest.webmanifest` y `sw.js`, pero tu archivo se llama `manifest.json`:
   entra en el proxy, no está en `PUBLIC_ROUTES`, y un visitante **sin sesión**
   recibe una redirección a `/entrar` en vez del manifiesto. Resultado: la PWA
   no se puede instalar desde la landing y el fallo es mudo (Chrome solo dice
   «manifest fetch failed»). **No edites `proxy.ts`** (es de F4): pide en
   `PEDIDOS.md` que añada `manifest.json` al matcher, y mientras tanto prueba con
   sesión iniciada. `sw.js` sí está excluido — ese lo tienes bien.

2. **`Permissions-Policy` de `next.config.ts` cierra cámara, micrófono,
   geolocalización, pagos y USB.** No cierra notificaciones ni push (no son
   features de esa cabecera en los navegadores actuales), así que tu bloque
   funciona. Pero **no añadas nada ahí para «asegurarte»**: la cabecera es de F4
   y esa lista es una decisión de producto documentada en un comentario de media
   pantalla, no una lista que se amplía a ojo.

3. **`showNotification` desde el `push` handler es obligatorio.** Si recibes un
   evento `push` y no muestras ninguna notificación, Chrome cuenta un «push
   silencioso»; tras unos pocos, **revoca el permiso del origen**. Si un aviso
   está agrupado o cae en horas de silencio, la decisión se toma **en el
   servidor** (`decidirEnvio`) y simplemente no se envía el push. Nunca la tomes
   dentro del service worker.

4. **`Notification.requestPermission()` en el primer render quema el origen.**
   La denegación por defecto de Chrome es permanente para ese origen y el usuario
   tendría que ir a la configuración del sitio para revertirla. El opt-in va tras
   un gesto explícito y tras una explicación previa. Este error no se puede
   deshacer con un despliegue.

5. **El endpoint de push cambia sin avisar.** El navegador rota la suscripción
   (actualización, limpieza de datos del sitio, reinstalación de la PWA). Sin la
   limpieza de `'gone'` y sin re-suscribir en `pushsubscriptionchange`, un
   usuario deja de recibir avisos sin que nadie lo detecte: no hay error, solo
   silencio. Maneja `pushsubscriptionchange` en `sw.js` y re-suscribe.

6. **Cachear `/api/**` en el service worker filtra contenido entre cuentas.**
   Si dos personas usan el mismo dispositivo —cosa habitual en una app de apoyo
   emocional— la respuesta cacheada del feed de una se le sirve a la otra. El
   `fetch` handler debe descartar por completo cualquier petición cuya URL
   empiece por `/api/`, y `activate` debe borrar las cachés viejas al cerrar
