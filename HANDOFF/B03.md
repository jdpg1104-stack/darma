# B03 · Publicar: composer y gate de reciprocidad

## Objetivo
Cuando esto termine, una persona puede escribir lo que le pasa y publicarlo, y la
regla que define Darma —escuchar a 3 personas desbloquea 1 publicación, la primera
es gratis— se aplica de verdad, en Postgres, con la UI limitándose a explicarla
con dignidad. Además, si el texto revela riesgo alto o crítico, la tarjeta de
recursos de ayuda aparece **en la misma respuesta** que confirma la publicación,
no en un correo ni en la pantalla siguiente. Es el bloque donde el producto y la
seguridad se tocan.

## Qué construir

1. **`components/composer/Composer.tsx` (`'use client'`).** Textarea con contador
   **20–5000** caracteres — exactamente el `CHECK` de `posts.body` en 0001; si
   pones otro número, la base rechazará textos que la UI aceptó. Estados:
   contador en gris, ámbar a partir de 4500, rojo fuera de rango. El botón se
   deshabilita fuera de rango pero **nunca** por reciprocidad: se deshabilita la
   acción, no la escritura (ver punto 4).

2. **Borrador local.** `localStorage` con clave `darma:borrador:v1`, guardado con
   debounce de 800 ms, restaurado al montar, borrado solo tras publicación
   confirmada por el servidor. **Nunca** `sessionStorage` ni cookie: el borrador
   no debe viajar al servidor. Si el servidor rechaza (reciprocidad, moderación,
   rate limit), el borrador **se mantiene**: la peor experiencia posible de esta
   pantalla es perder lo que alguien acababa de contar.

3. **Elección de tema y tipo.** `kind` ∈ `desahogo | pregunta | gratitud` (enum
   `post_kind` de 0001). `topic` de una lista cerrada exportada por
   `components/composer/temas.ts`: `ansiedad`, `duelo`, `soledad`, `trabajo`,
   `familia`, `pareja`, `salud`, `identidad`, `dinero`, `otro`. Cerrada y no texto
   libre para que B02 y B06 puedan filtrar e indexar sin normalizar strings.

4. **Estado de reciprocidad en la UI.** Lee de `/api/me` (B01) y usa
   `canPublish()`, `listensRemaining()` y `reciprocityMessage()` de
   `lib/reciprocity.ts`. **No reimplementes la regla ni el copy.** Muestra el
   mensaje exacto de `reciprocityMessage()` y un enlace a `/feed` para ir a
   escuchar. Regla de producto: **la palabra "crédito" no aparece nunca de cara
   al usuario** (está documentada en `lib/reciprocity.ts`; respétala).

5. **`assertNoPii` dos veces.** En el cliente, al perder el foco del textarea, para
   avisar antes de enviar ("hemos visto algo que parece un teléfono, ¿lo quitas?").
   Y **otra vez en el servidor**, como bloqueo duro → `contenido_bloqueado`. El
   cliente nunca es autoridad: cualquiera puede hacer `POST` con `curl` saltándose
   tu componente. El aviso de cliente es cortesía; el del servidor es la barrera.

6. **`POST /api/posts` — el orden de operaciones es el bloque entero.**
   1. `requireSesion()`.
   2. Zod: `{ body: string 20–5000, kind: enum, topic: enum }`. Nada más.
      **Ignora cualquier `authorId` que venga en el body** — no lo leas siquiera.
   3. `limitar('post:' + sesion.userId, 5, 3600)` → 5 posts/hora.
   4. `assertNoPii(body)` → `contenido_bloqueado` si falla.
   5. `const riesgo = await evaluarRiesgo(body)`.
   6. `insert into posts (...)` con el **cliente RLS**, `author_id = sesion.userId`,
      `risk = riesgo.nivel`. Aquí es donde dispara `trg_posts_reciprocity`.
   7. Si el insert falla con el código Postgres **`23514` (`check_violation`)** y
      el mensaje empieza por `reciprocidad:` → responde
      `{ ok: false, code: 'reciprocidad', message: RECIPROCITY_SERVER_REJECTION }`
      con **403**. Cualquier otro `23514` → `entrada_invalida` (es un CHECK de
      longitud, no el gate).
   8. Si `riesgo.nivel` es `high` o `critical`: `insert into crisis_events`
      (`user_id`, `ref_type='post'`, `ref_id`, `risk`, `resources_shown`,
      `country_code`) con el **cliente admin** — esa tabla tiene RLS activa y cero
      políticas a propósito. Un comentario de una línea justificándolo.
   9. Responde `{ ok: true, data: { post, recursos } }` con `recursos` **en la
      misma respuesta**.

7. **Tarjeta de recursos.** `components/composer/TarjetaRecursos.tsx`, renderizada
   inmediatamente tras publicar cuando `recursos != null`. Nunca bloquea ni oculta
   la publicación: el post se publica igual (CONTRATOS §9.2, "se prioriza, no se
   censura"). Tono: sin alarma, sin diagnóstico, con la línea de ayuda del país
   que devuelva `evaluarRiesgo()` y un botón de "hablar con alguien ahora".

8. **`PATCH /api/posts/[id]`** — edita `body` y `topic`. `authenticated` solo tiene
   `grant update (body, topic, state)`, así que no intentes tocar nada más.
   **Reevalúa el riesgo** en cada edición: editar es la vía obvia para meter texto
   de crisis esquivando la evaluación del insert. `DELETE` = `update state='removed'`,
   no un borrado físico (rompería el hilo de quien comentó).

9. **Voto.** `POST/DELETE /api/posts/[id]/voto` sobre `post_votes` (PK
   `(post_id,user_id)`). El contador lo mantiene `trg_post_votes_sync`: **no lo
   incrementes tú**. Rate limit `voto:<userId>` 60/min. Un voto **no** da karma y
   **no** cuenta como escucha (eso es B04); dilo en un comentario del archivo para
   que nadie lo "arregle" más adelante.

## Contrato que debes cumplir

```ts
// POST /api/posts
export interface CrearPostBody {
  body: string                                  // 20–5000
  kind: 'desahogo' | 'pregunta' | 'gratitud'
  topic: TemaDarma                              // components/composer/temas.ts
}

// 201 → { ok: true, data: RespuestaPublicar }
export interface RespuestaPublicar {
  post: PostCreado
  /** No null ⇒ píntalo YA, en esta misma pantalla. */
  recursos: TarjetaRecursosDatos | null
}

export interface PostCreado {
  id: string
  kind: 'desahogo' | 'pregunta' | 'gratitud'
  body: string
  topic: string | null
  creadoEn: string          // ISO-8601
}

export interface TarjetaRecursosDatos {
  titulo: string
  mensaje: string
  lineas: Array<{ nombre: string; telefono?: string; url?: string; horario?: string }>
  accionInmediata: { etiqueta: string; href: string }
}

export const TEMAS = ['ansiedad','duelo','soledad','trabajo','familia',
                      'pareja','salud','identidad','dinero','otro'] as const
export type TemaDarma = (typeof TEMAS)[number]
```

Errores posibles de `POST /api/posts`: `no_autenticado` (401), `reciprocidad`
(403), `entrada_invalida` (422), `contenido_bloqueado` (422),
`demasiadas_peticiones` (429, con `retryAfter`), `error_interno` (500).
`risk` **nunca** sale en la respuesta: la persona ve recursos, no una etiqueta.

## Consultas y rendimiento
- Publicar: **una** sentencia `insert ... returning id, kind, body, topic, created_at`.
  Los triggers `trg_posts_reciprocity` (UPDATE con lock sobre la fila de
  `profiles`) y `trg_posts_hot` corren dentro de la misma transacción; no añadas
  ninguna consulta previa de "¿tengo créditos?" — sería una condición de carrera
  con dos pestañas abiertas y una consulta extra en el camino caliente.
- La pantalla del composer hace **1** consulta (`/api/me`, ya cacheada por B01) y
  ninguna más. Índices implicados: PK de `profiles`, `idx_posts_author`.
- Voto: un `insert` sobre PK `(post_id,user_id)`; el conflicto de PK **es** la
  garantía de un voto por persona. `on conflict do nothing`.
- Presupuesto de `/publicar`: JS de cliente < 90 KB (es una pantalla con estado,
  pero solo un textarea), LCP < 2 s.

## Seguridad
- Zod estricto con `.strict()`: un body con campos de más se rechaza, no se ignora.
- `author_id` **siempre** de la sesión. Aceptar un `authorId` del cliente es la
  vulnerabilidad número uno de este tipo de app (CONTRATOS §6).
- `assertNoPii` en servidor obligatorio; el del cliente no cuenta.
- `evaluarRiesgo()` obligatorio en `POST` **y** en `PATCH`.
- Rate limit: 5 posts/hora por usuario, 60 votos/min. Además
  `post_ip:<hashIp>` 20/hora para frenar el registro masivo + publicación.
- **No pueden salir en la respuesta:** `risk`, `hot_score`, `state`, `author_id`,
  el mensaje crudo del error de Postgres, ni el nombre del trigger. El error de
  reciprocidad se traduce a `RECIPROCITY_SERVER_REJECTION`, que ya está escrito en
  `lib/reciprocity.ts`.
- Cliente admin **solo** para `crisis_events` y `moderation_flags`. Nunca para
  insertar el post ni para sortear el gate.

## Pruebas exigidas
1. Publicar con `posts_published = 0` funciona sin créditos (primer post gratis).
2. **Fallo:** con `posts_published > 0` y `listen_credits = 2` → el insert lanza
   `23514` y la ruta devuelve `code: 'reciprocidad'` y status 403, **no** 500.
3. **Fallo:** un `23514` por longitud de `body` (19 caracteres) se traduce a
   `entrada_invalida`, no a `reciprocidad`. (Este es el bug que se cuela.)
4. **Fallo:** body con `authorId` de otra persona → se ignora; el post queda a
   nombre del usuario de la sesión.
5. **Fallo:** texto con un teléfono o un email → `contenido_bloqueado`, aunque el
   cliente lo hubiera aceptado (simula la llamada directa a la API).
6. Riesgo `critical`: la respuesta trae `recursos != null`, se escribió una fila
   en `crisis_events`, **y el post existe y está `active`** (no censurado).
7. **Fallo:** sexta publicación en la misma hora → `demasiadas_peticiones` con
   `retryAfter` numérico en segundos.
8. **Fallo:** publicar con `banned_until` en el futuro → `reciprocidad`/`sin_permiso`
   según el mensaje del trigger, nunca un 500.
9. El borrador sobrevive a un rechazo del servidor y se borra tras un 201.

## Trampas conocidas
1. **Decidir la reciprocidad en la ruta.** Vas a querer escribir
   `if (!canPublish(...)) return error` antes del insert, porque da un error más
   bonito. Hazlo solo como pista opcional si quieres, pero **el insert tiene que
   ejecutarse igual**: `canPublish` mira un saldo leído hace segundos y dos
   pestañas gastan el mismo crédito. La autoridad es el `UPDATE ... RETURNING` del
   trigger, que toma el lock.
2. **Confundir los dos `23514`.** El trigger de reciprocidad y los `CHECK` de
   longitud levantan **el mismo** SQLSTATE. Si traduces todo `23514` a
   `reciprocidad`, un texto de 15 caracteres le dirá a la persona que le faltan
   escuchas, y se volverá loca. Discrimina por el prefijo `reciprocidad:` del
   mensaje, que está fijado en `posts_consume_credit()`.
3. **Mandar la tarjeta de recursos "en la siguiente pantalla".** Es más limpio de
   implementar y está prohibido por CONTRATOS §9.1. Va en el mismo JSON de la
   respuesta del `POST`, y se pinta sin navegación intermedia.
4. **Ocultar el post cuando el riesgo es crítico**, por prudencia. Es exactamente
   lo contrario de lo que hay que hacer: quien escribe desde ahí necesita ser
   escuchado. Se marca, se prioriza en la cola humana y se le dan recursos. No se
   esconde.
5. **Perder el borrador al fallar.** Un `router.push()` o un `reset()` del
   formulario en el `catch` y alguien pierde el texto que le costó media hora
   escribir. El `catch` no toca el borrador, punto.
6. **Reevaluar el riesgo solo en el insert.** El `PATCH` es el camino trivial para
   publicar algo inocuo y editarlo después. Si tu `PATCH` no llama a
   `evaluarRiesgo()`, has dejado la puerta abierta.
7. **Incrementar `upvote_count` a mano** al votar. Lo hace `trg_post_votes_sync`;
   hacerlo también tú lo duplica, y como `hot_score` deriva de él, corrompe el
   orden del feed de todos.
